# Why: apps/api Backend Structure

## Overview
`apps/api` is a Go REST API following a strict layered architecture:
`Router → Middleware → Handler → Service → Repository → Database`

Each layer has exactly one job. This makes every piece independently testable and replaceable.

## Layered architecture explained

```
Request arrives
      ↓
  Router (chi)       — which handler owns this URL + method?
      ↓
  Middleware         — is the JWT valid? log the request. rate limit check.
      ↓
  Handler            — parse + validate request body, call service, write JSON response
      ↓
  Service            — business logic: validate rules, coordinate between repos, fire Kafka events
      ↓
  Repository         — SQL queries only via sqlc, zero business logic
      ↓
  PostgreSQL
```

## Folder breakdown

| Folder / File | Why it exists |
|---|---|
| `cmd/server/main.go` | Only entrypoint — loads config, connects DB + Redis + Kafka, starts workers as goroutines, starts HTTP server |
| `internal/` | Go convention — code here cannot be imported by other modules, enforces encapsulation |
| `internal/config/config.go` | All env vars in one place — rest of codebase calls `config.Get()` never `os.Getenv()` directly |
| `internal/db/postgres.go` | Creates pgx connection pool — shared by all repositories, configured with max connections |
| `internal/cache/redis.go` | Redis client + typed helpers — used for sessions, share link TTL, rate limiting |
| `internal/middleware/auth.go` | Validates JWT on protected routes — extracts user from token and adds to `context.Context` |
| `internal/middleware/cors.go` | Allows the frontend origin (different port) to make API calls |
| `internal/middleware/logger.go` | Logs every request: method, path, status, duration, user ID if authenticated |
| `internal/middleware/ratelimit.go` | Token bucket per IP stored in Redis — prevents abuse without shared memory |
| `internal/api/router.go` | All route registrations in one file — one place to see every endpoint the API exposes |
| `internal/api/handlers/` | HTTP layer only — never contains business logic, only request parsing and response writing |
| `internal/services/` | Business logic — where rules are enforced, where decisions are made |
| `internal/services/auth.go` | bcrypt password hashing (cost 12), JWT sign with HS256, JWT verify and extract claims |
| `internal/services/designs.go` | CRUD, fork logic (copies elements + increments fork_count), star toggle |
| `internal/services/share.go` | Generates 8-char random slug, stores in Redis with TTL, falls back to Postgres for permanent links |
| `internal/services/ai.go` | Proxies to OpenAI/Anthropic, streams SSE response back to client, hides API key |
| `internal/realtime/hub.go` | WebSocket room registry using `sync.Map` — thread-safe, one room per share code |
| `internal/realtime/client.go` | One goroutine pair (readPump + writePump) per connected WebSocket client |
| `internal/realtime/message.go` | Typed WS message structs — `element_update`, `cursor_move`, `user_join`, `user_leave` |
| `internal/kafka/producer.go` | `Publish(ctx, topic, payload)` — fire and forget, logs errors, does not block handler |
| `internal/kafka/consumer.go` | Base consumer loop — reconnects on failure, used by all workers |
| `internal/kafka/topics.go` | Constants for every topic name — avoids typos, one place to audit all topics |
| `internal/workers/` | Long-running goroutines started in `main.go` — each consumes one Kafka topic |
| `internal/workers/analytics_worker.go` | Increments counters in Postgres: fork_count, view_count — decoupled from the API response |
| `internal/workers/room_worker.go` | Persists canvas state snapshots from WebSocket rooms back to Postgres periodically |
| `internal/models/` | Plain Go structs — what a Design, User, Room looks like. No methods, no DB tags. |
| `sqlc/queries/` | Hand-written SQL files — sqlc reads these and generates type-safe Go functions |
| `sqlc/generated/` | Auto-generated by `sqlc generate` — NEVER edit manually, always overwritten |
| `openapi/openapi.yaml` | Auto-generated by swaggo from handler annotations — source of truth for TypeScript codegen |
| `migrations/` | Versioned SQL files managed by goose — `up` creates tables, `down` reverses them |
| `.air.toml` | Air config — watches `.go` files, recompiles and restarts the server on every save |
| `Makefile` | Shortcuts: `make run`, `make test`, `make migrate`, `make sqlc`, `make swagger` |

## Why sqlc instead of GORM?
- You write real SQL and learn it properly — not ORM-translated SQL
- Generated code is fully type-safe — no `interface{}`, no runtime surprises from column name typos
- Queries are explicit — you always know exactly what SQL runs and when
- 0 reflection at runtime — faster than GORM

## Why goose for migrations?
- SQL-based migrations — you write plain SQL, no DSL to learn
- Versioned and reversible — every migration has a corresponding `down` file
- Works perfectly with Docker `migrate` service — runs on startup, exits cleanly
